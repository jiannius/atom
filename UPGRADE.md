# Upgrading to atom 4

Each change that breaks a host is listed once, under the release that made it. Every section ends with an **atom:upgrade:** line that says which of its entries the codemod rewrites (**Automated**) and which it only lists in `ATOM-UPGRADE-TODO.md` (**Reported**), by the check id that `php artisan atom:upgrade-check` prints; the rest of a section is a change of look that no command acts on.

**Read "PHP globals: dates and macros" first:** every date in your app changes type and string form unless you add one line, and nothing throws for the string change. `atom:upgrade` adds that line for you.

## The order

1. **Size the move (on 3.38 or later).** `php artisan atom:upgrade-check` reads your app, writes nothing, and lists every break below with `file:line`, a severity and whether the codemod fixes it. See the README, "Moving an app to v4".
2. **Move the editor columns to JSON, still on 3.x.** Switch each `AsEditorContent` cast to `AsTiptapContent`, then `php artisan atom:tiptap-migrate` (a dry run), `--force`, `--compare` (read the review file), `--prune-backups` once you have signed it off, and `php artisan atom:tiptap-migrate --status --for-v4` exits 0 when nothing is left. The steps are under "The legacy editor". Do this before step 3: the class is gone in v4.
3. **Require v4.** See "Installing a pre-release" while v4 is one.
4. **Preview the codemod.** `php artisan atom:upgrade --dry-run` prints a unified diff of every file it would change and the `ATOM-UPGRADE-TODO.md` it would write, and writes nothing. It ends with the gate: `atom:upgrade` refuses to write while `atom:tiptap-migrate --status` is not ready (a cast left on `AsEditorContent`, a row not migrated or flagged, or a status it cannot read, for instance with no database).
5. **Apply it.** Commit your work first, run `php artisan atom:upgrade`, and read the diff. A second run changes nothing. `--path=` points it at another directory.
6. **Work through `ATOM-UPGRADE-TODO.md`.** It lists, by section of this guide and with `file:line`, everything that is left: the sites it only reports (the JS globals, the `$wire` helpers, the date and macro calls, the classes you put on restyled components, your tests), what it declined to rewrite and why, the traits it chose and the evidence (text cannot see everything, so check them), and the accent colour. It is rewritten by every run.
7. **Run your tests and look at the pages.** The look changed everywhere. Delete the TODO file when you are done.

## Installing a pre-release

Pin an exact version: `composer require jiannius/atom:4.0.0-alpha.N` (the number is on the releases page). Composer accepts an exact pre-release version even under `"minimum-stability": "stable"`, so `composer.json` needs no other change. A range is different: `^4.0` alone never picks the alpha; `^4.0@alpha` does, or a lower `minimum-stability`.

## Tokens

**CSS integration.** (Automated for a Tailwind entry file in the skeleton-project shape.) Delete your atom `@source` lines and the theme block copied from skeleton-project (the font, `primary`, the zinc remap, `muted`, `accent`, the `border-color` base rule). Add `@import '../../vendor/jiannius/atom/resources/css/atom.tailwind.css';` after `@import 'tailwindcss';`. Then set your brand colour as `--color-accent` in `@theme`, and do not set `accent-foreground` unless you must. A derived colour you do set goes in `@theme` too, not in a plain `:root` rule: `accent-soft` and `accent-ink` are inline tokens, which utilities read where they are used. Overriding `--color-accent-ink` changes the `accent-ink` utilities only: `accent-content` and the focus ring read atom's `--atom-accent-ink` role directly (so a nested `.dark` island keeps its own values), and a `--color-accent-ink` override does not reach them.

**Root size.** The 14px root is gone; spacing utilities follow Tailwind (`p-6` is 24px, not 21px). Remove any `html { font-size }` override.

**Type sizes and density.** `text-xs`/`sm`/`base` follow the density profile of the page: compact (`layouts.sidebar`) renders them at 12/13/14px, comfortable (a bare `<atom:html>`, `layouts.auth`) at 13/14/15px. Pass `density="compact"` or `"comfortable"` to `<atom:html>` to change a page, or set `data-atom-density` on any element for a subtree. A touch device (`pointer: coarse`) gets taller controls and rows in either profile. `text-lg`, `text-xl` and `text-2xl` are now 16, 18 and 22px, and `font-medium` and `font-semibold` are weights 510 and 590 (Geist is a variable font, so they draw as asked).

**Browsers.** The derived accent colours (`accent-foreground`, `accent-hover`, `accent-ink`) and the focus ring use CSS relative colour: Chrome and Edge 119, Safari 16.4, Firefox 128. Below that floor atom falls back to plain colours: a white label on the accent, the accent itself for hover and for accent text, and a blue (`#3b82f6`) focus ring, so the focus ring stays visible and a dark accent keeps a readable label. A light accent does not: the label is always white, so on a light accent such as `#f5c518` it is about 1.6:1 and hard to read. Hover shows no change.

**Accent fallback.** If your app does not set `--color-accent`, the accent is near-black (`#1c1b18`) in light and flips to a near-white (`#ecebe8`, with a near-black label) in dark, so a primary button is still seen on the dark canvas (3:1 against it, its label 4.5:1). The hover, the ink, the soft tone and the focus ring follow the flip, including inside a nested `.dark` island. The flip uses CSS `light-dark()` (Chrome and Edge 123, Safari 17.5, Firefox 120); an older browser keeps the near-black in both themes. An app that sets its own `--color-accent` is not affected: its colour is the same in both themes, and you can still set one accent per theme yourself.

**Font.** Geist is the default. Pass `fonts="inter"` to `<atom:html>` to keep the old font, or `:fonts="false"` to load none and use the system fonts.

**Remove the font you loaded for the old design.** atom serves Geist and Geist Mono itself: the files come from its own `/atom/{file}` route and `<atom:html>` (so every shell) preloads them. Delete the Vite font plugin (a Bunny or Google Fonts plugin, and its entry in `vite.config.js`) and any `@font-face` or `--font-sans` you wrote for the old font, or the page downloads a second font for nothing. Keep one only if you pass `fonts="inter"` (or another family) on purpose.

**Delete the copied `border-color` base rule.** Tailwind 4 draws a border in `currentColor`, so apps copied a base rule that gives every element a grey default border, in different shapes (for example `border-color: var(--color-gray-200, currentColor)` on `*, ::after, ::before`, alone or inside `@layer base`). Delete whatever rule does that, whatever its colour or selector list. atom now sets the default border colour itself, on `*`, `::after`, `::before`, `::backdrop` and `::file-selector-button`, from its `--atom-border` role (so it follows light and dark), in a layer so your own rule still wins. A copy left in place wins, and every border that has no colour utility of its own draws in the copied colour, not atom's.

**atom:upgrade:** Automated: `css-atom-source`, `css-skeleton-theme`, `css-border-color-rule`. Reported: `css-root-font-size`, `css-old-font`. In a Tailwind entry file with a plain `@import 'tailwindcss'` and atom's `@source` lines, the codemod removes atom's three `@source` lines, every declaration of the skeleton-project theme block whose value is the skeleton's (one you changed stays, and is listed) and the copied `border-color` base rule of the skeleton's shape, and adds `@import` of `atom.tailwind.css` after Tailwind's, with the path worked out from the file's own depth. If `--color-primary` is your own colour it is also set as `--color-accent` in `@theme` (your `primary` stays). The rest of the file is left byte for byte; a file that is not that shape is left alone and listed with the reason. The root size, density, browser and accent notes above are a change of look: the TODO states what `--color-accent` is.

## Shells

`layouts.header` is new: use it for apps with about 6 or fewer top-level sections. It takes the same slots and props as `layouts.sidebar`, including the same `nav` markup, so an app can choose the shell per user (for example, the top nav for a role that sees only one or two modules). `<main>` is still unpadded; padding now comes from `<atom:page>`.

**What changes in the shells you already use.** `layouts.sidebar` is restyled: a 228px side surface, 28px nav rows with 16px icons, and a 48px sticky top bar that is now shown at every width below `lg`, and from `lg` up only when it has something to hold (it holds the new `crumbs` and `actions` slots, and the dark toggle when `dark` is set, which used to show on small screens only; remove a toggle you put in `navfoot` yourself). Both shells also take new slots, `context` (a workspace switcher) and `search`. Navigation items now carry `aria-current="page"`, and a `navlist.group` heading is 12px and no longer uppercase. `layouts.auth` is restyled with the comfortable density and a plain canvas (the dark gradient is gone).

**A class on a headed `navlist.group`.** `<atom:navlist.group heading="..." class="...">` now puts its attributes on the group's root element (the heading, the items and the header shell's dropdown trigger), not on the inner list of items as before. A class you passed to space or style that list now applies to the whole group; move it onto the items or wrap them. A group with no `heading` is unchanged.

**The top nav switches to a menu below 1024px.** `layouts.header` shows its items as a bar from `lg` up (below that the logo, context, items and account do not fit side by side). Below `lg` the nav is a menu, with the `context` slot and then the `search` slot as the first two rows of the panel. The `search` slot is printed once and shown three ways: that full-width row below `lg`; from `lg` to `xl` (1280px) a search icon button in the bar opens it in a popover (Enter or Space opens it, focus goes to the first input, Escape closes it and returns focus to the button); from `xl` up it is inline in the bar.

**Items that do not fit the bar move into "More".** From `lg` up the top nav is priority-plus: the top-level items of your `nav` slot stay in the bar while they fit, and the rest move, in order, into a trailing "More" dropdown, so a bar with long labels or counts never overflows or runs under the actions. A group that moves shows as a labelled section inside "More"; when the current item has moved, "More" carries the current underline. Nothing to configure and no fixed widths: it is measured in the browser. "More" holds a copy of each moved item (the original stays in the bar, hidden), so a host that selects nav links in JS should scope its selector to `[data-atom-header-nav] > [data-atom-navlist]`, or skip `[data-atom-more-copy]`. In the bar, Escape closes the innermost thing that is open (a dropdown, the search popover, "More", then the menu panel) and nothing else. A `profile` slot with no `dropdown` is plain content in both shells, not a button.

**The `dropdown` slot is the account menu: pass menu items only.** Both shells wrap the slot in `<atom:menu>` themselves and print a default profile card (avatar or initials, then the name and email of `auth()->user()`), so put `<atom:menu.item>` rows and separators in `<x-slot:dropdown>` and nothing around them. A menu of your own around them double-wraps it (a second panel inside the first). Where the card sits depends on the shell: in the sidebar from `lg` up it is the trigger row at the foot of the side surface (the menu behind it holds your items only); in the sidebar's top bar below `lg`, and in the top nav, it is the head of the menu, above a separator and your items. The optional `profile` slot replaces the card in whichever place it sits. The avatar is read from `$user->avatar`: a URL is drawn as the image, and a user with no such attribute (or no value) gets initials. A model that throws on an attribute it does not have (`Model::preventAccessingMissingAttributes()`) counts as having none (only that exception: an accessor that throws something else still surfaces). The same goes for `name` and `email`. The initials come from `$user->initials()` when your User model has a public method of that name that returns a non-blank string. A model without one is not an error, and neither is an `initials()` that is protected (an Eloquent `Attribute` accessor) or returns something else (or a blank string): they are the first letters of the first two words of `$user->name`, uppercase (`tan joon long` gives `TJ`). Define `initials()` on the model to change that.

**Choosing the shell is yours.** Atom does not switch on an item count: it renders the nav before it knows where the nav goes. Decide in your own app layout, for example `<x-dynamic-component :component="$user->modules()->count() <= 2 ? 'atom::layouts.header' : 'atom::layouts.sidebar'">`. The choice is per page load; a role does not change mid-session, so `wire:navigate` never crosses shells.

**atom:upgrade:** Automated: none. Reported: `navlist-group-class`, `shell-dropdown-menu-wrap`. The restyled shells, `layouts.header`, the narrow-screen menu and "More" are a look change and a new component: nothing to run.

## Page components

Replace copied `partials/section`, `breadcrumbs` and `heading` shells with `<atom:page>`. This is recommended, not required.

New, and additive: `<atom:page>`, `<atom:page.header>`, `<atom:page.tabs>`, `<atom:status>`, `<atom:stat>` and `<atom:stat.group>`. Start a screen with `<atom:page>` (it pads the page; the shell's `<main>` still does not) and `<atom:page.header>`, which holds the crumbs, the title, a status beside it, key facts, the actions and the one primary action for the record's current state. A level-1 `page.header` replaces the layout's hidden fallback `<h1>`, so a page that uses it has one `<h1>`. If your own partial shows crumbs in the header too, drop one of the two: the shell's `crumbs` slot or the header's `crumbs` prop.

**Which crumbs to use.** The header's `crumbs` prop is static: a list you pass in, drawn as links (the last is the current page), remembering nothing. The other kind is `<atom:breadcrumbs />` inside `@persist('breadcrumbs')`, a trail built from the pages the user actually came through, and the only thing that draws the Livewire component's `breadcrumbs()` method. That trail also keeps the URL the user left each page with (its filters and `?page=`), so a crumb or Back returns to the filtered listing, where the static prop goes to the `href` you wrote. A page that uses the header's `crumbs` instead of the persisted trail loses that "where you came from" trail, and its `breadcrumbs()` method feeds nothing there (`$_breadcrumbs` is still filled; nothing draws it). Choose the persisted trail for a listing people filter and come back to, and for a record reached from more than one place. Choose the header's `crumbs` for a fixed hierarchy (Settings, Billing) or a page with no Livewire component (the trail reads the page's component, so without one it has nothing to show). One on a page, never both.

**`<atom:empty>` is reworked.** It takes `kind` (`first-use`, `no-results`, the default, or `error`) and an `action` slot for the next step. Nothing you pass today stops working: with no `kind` it still reads "No Results" with the inbox icon, and `icon`, `heading`, `subheading`, `size`, `subtle` and the default slot behave as before. What changes is the look (design tokens in place of the zinc palette, a 16px heading, centred text) and the large state's icon, which draws itself in once, in about a second; not at `size="sm"` or `subtle`, and not under `prefers-reduced-motion`. A class or test that matched `py-8` or `bg-zinc-100` on it needs updating.

**Status.** A `badge` stays as it was. Use `<atom:status>` where a state is a word with a dot (`tone`: `neutral`, `info`, `success`, `warning`, `danger`, `accent`; `running` pulses the dot): it reads the role tokens, so it follows the theme and the accent without a `dark:` pair.

**atom:upgrade:** Automated: none. Reported: none. The page components are additive and recommended, not required.

## Lists, forms and the timeline

Recommended: frameless tables inside panels; `numeric` on money columns; `form.section` for settings and forms. Everything here is additive (new props and components) except the look changes listed last.

**New.** `<atom:table frameless>` (no outer box, for a table inside a panel your page draws, under `<atom:table.views>` and `<atom:table.toolbar>`), `numeric` on `table.column` and `table.cell`, `<atom:table.toolbar>`, `<atom:table.views>` with `<atom:table.views.item>`, `<atom:form.section>`, a `bar` prop on `<atom:form.actions>` (the page save bar) and `<atom:timeline>` with `<atom:timeline.item>`. Read the four pattern pages (`resources/views/docs/patterns/list-page.blade.php`, `document-page`, `form-page`, `slide-over-form`) and copy their structure. Their data is invented.

**Saved views.** Bind `<atom:table.views wire:model.live="filters.view">` and pass `:counts` as an array keyed by the item's `value`, or a closure that gets the `value` and returns the count: atom never runs a count query, and a closure runs once per item on every render. With `WithUrlFilters`, declare `'view' => 'all'` in `urlFilters()` and have `isUrlFilterValid()` know the values; do not lock the property. Pass `:current` as well so the first paint is right.

**A view change clears a bulk selection, and does not reset the page.** `table.views` tells the table, as a filter does, so ticked rows are dropped when the view changes. Reset the page where you reset it for any filter (`updatedFilters()` calling `$this->resetPage()`); atom's filters do not do it for you.

**An item in a `@foreach` needs a `wire:key`** in `<atom:timeline>` (its folded state is Alpine's), and a `DateTimeInterface` `time` shows in the viewer's timezone.

**The toolbar belongs in the table's `header` slot, and counts do not.** In `<x-slot:header>` the table draws the strip around the toolbar and swaps it for the bulk-action bar while rows are ticked. The slot is an Alpine template, so text the server renders into it is not refreshed by a re-render (this was always so for the `header` slot): put a count or a total below the table. A toolbar placed elsewhere takes `strip`.

**The save bar is full width, its content on the page column.** `<atom:form.actions bar>` is sticky at the bottom of the screen. Its blurred surface and hairline run the full width of the screen's content area: from the sidebar's edge to the screen's right edge in the sidebar shell, from edge to edge in the top-nav shell. Its start slot and buttons stay aligned to the page column, whatever the page's `width`. The box itself is the page's padding box, padded by two CSS variables `<atom:page>` now sets (`--atom-gutter-s`, `--atom-gutter-e`; the page's bottom room is `--atom-page-pb`); the surface and the hairline are `::before` and `::after` that fill that box, and atom.css carries them on to the screen edge with a `box-shadow` spread clipped by a `clip-path` (the shells' `<main>` sets `--atom-bar-left` and `--atom-bar-right` for it). A shadow takes no layout room, so nothing scrolls sideways because of it, the page is never clipped, and it does not print smaller. The sidebar shell's bleed assumes the page starts at `<main>`'s content edge: do not put `mx-auto` on `<atom:page>` there. Outside a shell and an `<atom:page>` the variables are missing: the surface is the bar's own box, with a 16px gutter and no bottom room. In a modal or a slide-over keep using `sticky` (what `form.modal` draws).

**What changes in a table you already have.** No prop is removed, but the look moves with the tokens. A header cell is a 12px label at weight 510 in the muted tone, no longer uppercase or letter-spaced; its padding matches the cell's, so the two line up. A cell is on the row tokens: `px-row py-row leading-row` (9px by 12px, a 13px line at 1.35 in compact density) with a floor height (`--atom-row-min-h`: 40px compact, 44 comfortable, 48 on a touch device), not the old `py-3 px-4`. A table that sat in rows of 20px text is therefore a few pixels shorter, and one with a two-line cell is no longer squeezed. The header row no longer has the grey fill (`bg-zinc-100`, transparent in dark): it is on the panel's surface, with a hairline under it. A sortable header's dotted underline sits at `underline-offset-4` (it was 5) and takes the foreground colour. The row-actions cell (`table.actions`) is on the row tokens too, not `py-3 px-4`. The framed card is `rounded-panel border bg-surface` with no shadow, and the row hover is a faint fill. The table root is `min-w-0 max-w-full`, so a wide table inside a grid or flex parent (`<atom:page>` is one) scrolls inside its own box instead of widening the page: remove a `min-w-0` or `overflow-x-auto` wrapper you added to work around that. A test or a style that matched `uppercase`, `py-3`, `bg-zinc-100` or `rounded-lg` on a table needs updating.

**`form.actions sticky`** (the modal footer) now sits on the `surface` token (it was `bg-white dark:bg-zinc-900`, which are the same colours), is `z-10` (it was `z-1`), and its top border uses the border token (it was `border-zinc-100 dark:border-zinc-700`, a lighter line in light mode).

**atom:upgrade:** Automated: none. Reported: none. Everything here is additive except the look changes, which no command acts on.

## Controls

Components use atom's tokens; remove overrides that patched the old look. Tag APIs are unchanged except where this section says so.

**`type="submit"` and `type="delete"` no longer add an icon by themselves** (a check and a trash can used to appear). Pass `icon="check"` or `icon="delete"` where you want one; a button with a label and no `icon` is a label.

**Button variants.** The tiers are `primary` (the solid accent, one per view), the default (bordered, no shadow) and `ghost`; `link` is text. Use `primary` for the accent button: `accent` still works, as an alias of it. `danger`, `warning`, `success` and `info` are solid tone fills, and `inverted` gives a tone's tint (`type="delete"` is the danger tint). `variant="outline"` and `"secondary"` were never defined and still draw the default tier, which is bordered: write the default (no `variant`). `facebook`, `google`, `linkedin`, `whatsapp` and `telegram` are the default tier with the brand's icon; they no longer paint the brand colour. `ghost` takes `color` (`accent`, `danger`, `warning`, `success`, `info`; `primary` still works as `accent`) and tints its text and its hover fill instead of filling solid on hover. Before this release `variant="primary"` was a near-black button that ignored your accent: if you relied on that, say `variant="primary"` and set `--color-accent`.

**Sizes come from the control token.** A button, input, select, date picker, time picker and tel field are 28px high in the compact density, 32 in comfortable and 40 on a touch device. A button's `sm` and `xs` sit 4px and 8px under that and `md` and `lg` 4px and 8px over (they were 32, 24, 48 and 56). Hosts that wrote `size="sm"` for a normal button next to a field should drop it: the default is the field's height. The text is 13px (14 in comfortable) and the icons 16px, where they were 20px. The OTP box is 40px square.

**Fields.** One recipe for every text control: a control border on the surface (a new role, `control-border`, which the field, the default button, the select and date triggers and the dropzone use: the hairline in light, a solid grey in dark), a 7px radius, no shadow, `fg-subtle` placeholder, sunken when disabled, the danger tone when `invalid` or in error. The ring is atom's `:focus-visible` outline, 2px, hugging the field's border (which takes the focus colour), where it was a 1px `focus:` outline in a grey. A select's option rows are 28px rows, and the calendar's selected day is `accent-ink` (it holds 3:1 on the panel in dark whatever your accent).

**Checkbox, radio, toggle.** A checkbox is 16px (was 18) with a 4px radius and a radio is now a 16px circle (it was a rounded square). A toggle is 36 by 20. Unchecked ones are stroked `fg-subtle`, checked ones are `accent-ink` with the mark in the surface colour, and none has a shadow.

**Slider, rating and uploader.** The slider's fill and thumb are `accent-ink` (they were near-black), its track 4px, with no thumb shadow; the rating's filled stars are `accent-ink` (they were amber `#f59e0b`) at 20px (they were 24px). A host that wants amber stars sets `color` on `[data-atom-rating-fill]`. The dropzone is a dashed hairline at radius 7.

**Calendar day cells are 36px.** A day in the date picker's calendar is 36px square (it was 40px), with 13px numbers (14 in the comfortable density), and the month label is that size at weight 590 (it was 20px). A host that sized the panel around the old cells needs to look at it.

**`button.group` lost `overflow-hidden` and its shadow.** The joined buttons share one hairline and keep the radius only at the group's two ends, so a focused button's ring is no longer cut off (a focused one is raised); the group draws no shadow of its own. A host that relied on the group clipping its contents, or on its shadow, has to supply that.

**New utilities.** `h-control-xs|sm|md|lg` and `min-h-control` follow the control token like `h-control`.

**Breaks a test.** A test or a style that matched `bg-primary`, `bg-white`, `shadow-xs`, `h-10`, `rounded-lg`, `size-4.5` or the focus classes on these components needs updating; the primary button is `bg-accent`.

**Dark check.** The dark-mode contrast check covers the 3a components and variants the two dark-mode hosts render: button (primary, default, ghost with a colour, danger, link, delete, submit, the Google and Facebook variants, sizes xs, sm and default, icon-only), input (text, email with chips, number, password, tel, colour, file through the uploader, OTP, icon, prefix and suffix), select (native, listbox single, multiple and searchable, filter), date picker (date, range, with time), textarea (autoresize, read-only), checkbox (caption, align start, card group), radio (group, card), toggle and uploader. Each text role is measured against its own surface at 4.5:1, and the boundaries and rings that identify a control at 3:1, in dark and light and for three accents (`tests/e2e/controls-*.spec.js`). Not measured, and left token-driven: the slider and the rating (no host uses them) and the standalone time picker (reached through the date picker's time row). The box of a control holds 3:1 in dark: `--atom-control-border` is `#726e65` there (3.6:1 on the surface it sits on, measured on a text field, a select, a date trigger and the default button; 3.1 on a raised panel), so the box reads clearly. In light it stays the design's 17% hairline, 1.41:1: an accepted exception to the 3:1 of WCAG 1.4.11, recorded in the spec report. `border-strong` is unchanged (panels, chips, dividers); utilities `border-control-border` and `bg-control-border` exist. Checkbox, radio and toggle, which have nothing else to identify them, hold 3:1 in both themes.

**atom:upgrade:** Automated: none. Reported: `button-implicit-icon`, `button-variant-undefined`, `button-variant-brand`, `button-variant-primary`, `button-size-prop`. The other entries are a look change.

## Data display

Components use atom's tokens; remove overrides that patched the old look. Tag APIs are unchanged: no prop was added or removed. This batch is the table (every part), `badge`, `card`, `callout`, `dd`, `list`, `avatar`, `pagination`, `progress`, `skeleton` and `kbd`, and the small ones that go with them (`profile`, `placeholder-bar`, `navlist.badge`).

**Badge colours: `amber`, `indigo` and the rest map to tones.** A badge is now a borderless pill on the tone tokens (the tint with its own ink, 4.5:1 or more in light and dark), the same recipe as `<atom:status>` without the dot. `color` takes a tone, `black`, a hex, or any colour name a host might already pass, and a name that was never defined (`amber`, `indigo`, `teal`...) used to fall back to grey without saying so. The mapping:

| `color` | Reads as |
| --- | --- |
| `neutral`, `gray`, `grey`, `zinc`, `slate`, `stone`, `white`, none, and any name not listed here | neutral |
| `info`, `blue`, `sky`, `cyan`, `indigo` | info |
| `success`, `green`, `emerald`, `teal`, `lime` | success |
| `warning`, `yellow`, `amber`, `orange` | warning |
| `danger`, `error`, `red`, `rose` | danger |
| `accent`, `primary`, `purple`, `violet`, `fuchsia`, `pink` | accent (the colour of your brand, so purple is whatever your `--color-accent` is) |

**Dark check.** The dark-mode contrast check covers the 3d components and variants the two dark-mode hosts render: heading, subheading, caption, label and error (in a field), link (on the canvas, in a card and a sunken card, and in a callout of each tone), separator, the editor (the content with a heading of each level, a link, a mention, a quote, a list, a table, inline code and a code block; the toolbar's glyphs; the placeholder; the field frame), the chat composer, the calendar (month and week, items of every colour and of a hex, the selection, a pending item, the day list), `copy`, `sharer`, `embed` and `whatsapp`, and the docs pages as pages. **atom:upgrade:** Automated: none. Reported: `chart-color-unknown`, `link-colour-override`. The other entries are a look change.

## Livewire traits

**`AtomComponent` is deleted (no alias).** Replace `use AtomComponent;` with only the traits the component needs, from `Jiannius\Atom\Traits\`:

- `WithTable`: the component renders `<atom:table>` or sorts through `toTable()`;
- `WithBreadcrumbs`: the component defines `breadcrumbs()`;
- `WithEditor`: the component renders `<atom:tiptap>` with image upload (it brings `WithFileUploads`);
- `WithRecaptcha`: the component uses `<atom:form recaptcha>` and `verifyRecaptcha()`;
- plus Livewire's own `WithPagination` for a paginated list and `WithFileUploads` for an uploader. `AtomComponent` forced both on every component; neither is implied any more.

A component that renders `<atom:table>` (or a sortable column, a checkbox cell, the trashed toggle, the pager), the tiptap image toolbar or `<atom:form recaptcha>` without the matching trait now throws an error naming the trait and the component class, and so does a component that defines `breadcrumbs()` without `WithBreadcrumbs` (nothing would call it any more). The check happens when the component's view renders, so table markup rendered to a string in `mount()` or an action (an export, a PDF, a mail body) is not an error. In v3 `AtomComponent` called a component's `breadcrumbs($b)` method on every mount; in v4 a component with its own `breadcrumbs($b)` method (one that takes the builder) and no `WithBreadcrumbs` throws at mount, naming the trait. A method that takes no parameter, a method carrying a Livewire attribute (a `#[Computed]` property named `breadcrumbs`), and a component or inherited method that comes from a Composer package (`vendor/`, including a path-repository symlink and a custom `vendor-dir`) are ignored. That includes your own modules when they are installed as Composer path packages: a `breadcrumbs($b)` method in one of those is never flagged, so give such a module the trait yourself. `toTable()` reads the table state only from a component that uses `WithTable`: on any other it applies no sort, even if the component declares its own `$_table`.

**The helpers are PHP-only.** `$this->toast()`, `modal()`, `alert()`, `confirm()`, `command()`, `wirekey()` and `action()` work unchanged in PHP and Blade on every Livewire component (they are macros on `Livewire\Component`, so no trait is needed), but they can no longer be called from the browser: `$wire.toast(...)` and the like are refused with a "method not found" error. Search your JS and Blade for `$wire.toast`, `$wire.alert`, `$wire.confirm`, `$wire.modal` and `$wire.command`; for the same names as Livewire directives with no `$wire.` prefix (`wire:click="toast('Saved')"`, `wire:submit`, `x-on:click="$wire.toast(...)"`); and for event mappings that target a helper (`protected $listeners = ['saved' => 'toast']`, `#[On('saved')]` on a method with one of these names), which now fail with `EventHandlerDoesNotExist`. Use `atom.toast(...)`, `atom.alert(...)` or dispatch `atom-toast-show` instead. A component that defines one of these names as its own method keeps its method, as before; define a shadowed `action()` `protected`.

**Hook names follow the traits.** `mountAtomComponent`, `updatingAtomComponent` and `updatedAtomComponent` are now `mountWithBreadcrumbs`, `updatedWithTable` and `updatedWithEditor` (the table sort gate is no longer a hook). Only a component that overrode or called one of them by name needs a change. Do not name a property or a method after a trait hook (`withTable`, `withEditor`, `withBreadcrumbs`, `withRecaptcha`, `withUrlFilters`, `updatingWithTable` ...): Livewire calls a trait's hook for a property of the same name too, so a string-valued one runs the hook confusingly. The `raw:` table-sort gate does not depend on any of these names: it is a listener on Livewire's `update` event (registered to run before any of your `updating*` hooks) for components that use `WithTable`. Do not put `_table` in a component's `queryString` or `#[Url]`: a URL is read into the property before `mount()`, through no update event, so a `WithTable` component that does throws at mount. `WithUrlFilters` reserves the `page` query key only on a component that uses `WithPagination`, which is now the component's own choice.

**atom:upgrade:** Automated: `use-atom-component`. Reported: `wire-helper-browser`, `wire-helper-listener`, `trait-hook-name`, `table-state-in-url`. The codemod rewrites each `use AtomComponent;` in a class body (a single-file Blade component too; not in `tests/`) to the traits the component's view, the partials it includes and its methods call for, adds the `use` imports in alphabetical place and drops the old import. Traits already in the class are not repeated. It lists the traits it chose, with the evidence for each, in the TODO, because text cannot see everything: a table rendered from a partial three levels down, `breadcrumbs()` on a parent class, a trait a base class should carry. The rule is that it declines (the line stays, and the TODO says why) whenever it cannot be sure: an abstract class or a trait, a class another class extends, a file that declares several classes, a class whose view it cannot find or that has no `render()` with a literal `view()`, a `use` with conflict rules or a comment in it, a file with a braced `namespace { }` or an import it cannot read. A host's own trait that happens to be called `AtomComponent` is not atom's: it is reported, not rewritten (check whether it wraps atom's). A loud "trait missing" error on v4 is better than a silently wrong guess; add the traits to those by hand.

## PHP globals: dates and macros

**Warning: without one line in `AppServiceProvider::boot()`, every date in your app is a different class, is mutable, and prints differently, and some of that fails silently.**

**Dates are the framework's again.** atom no longer swaps Laravel's `Date` facade to `Jiannius\Atom\Services\Carbon`, so `now()`, `today()` and a model's date casts return Illuminate dates: **mutable**, with no `->pretty()`, `->local()`, `->recent()` or `->toDateRangeString()`. Add this to `AppServiceProvider::boot()` to keep immutable dates and those methods on every date:

```php
use Illuminate\Support\Facades\Date;

Date::use(\Jiannius\Atom\Services\Carbon::class);
```

Search your PHP and Blade for `->pretty(`, `->local(`, `->recent(` and `->toDateRangeString(`: each call on a model date or on `now()` throws "Method ... does not exist" without the line. A host that does not want the swap can call `carbon($date)->pretty()` (or `Carbon::instance($date)`) where it needs them; `Jiannius\Atom\Services\Carbon`, `Carbon::getLocalTimezone()` and the `carbon()` helper are unchanged, and atom's own code (`breakdown()`, the calendar, the timeline) works on either kind of date. Code that relied on a date being immutable (`$date->addDay()` leaving `$date` alone) now changes the date in place without the line: use `->copy()` or add the line.

**The string form of a date changes, with no error.** `Services\Carbon::__toString()` returns ISO 8601 with a `Z` (`2026-03-01T10:00:00Z`); the Illuminate default is `Y-m-d H:i:s` (`2026-03-01 10:00:00`). Without the line, everything that turns a date into a string changes output: `{{ $date }}`, `(string) $date`, concatenation and interpolation, a cache key built from a date, and a date bound as a string. `json_encode()` and `toJson()` are the same either way (both print `2026-03-01T10:00:00.000000Z`). Search for dates printed or concatenated without `->format()`, and for cache keys and stored strings built from them. Also search for `instanceof Jiannius\Atom\Services\Carbon` and for parameters or return types typed `Jiannius\Atom\Services\Carbon`: a model date no longer matches them (type to `Carbon\CarbonInterface` instead). The `Date::use()` line above restores all of it: the class, the immutability, `pretty()`, `local()`, `recent()` and `toDateRangeString()`, and the ISO string form.

**Macros removed.** atom itself does not call any of these:

- `Request`: `subdomain()`, `hostWithoutSubdomain()` and `isLivewireRequest()` (use `app('livewire')->isLivewireRequest()`);
- `Str` and `Stringable`: `dotpath()`;
- Eloquent and query `Builder`: `tableHasColumn()` (use `Schema::hasColumn()`);
- `ComponentAttributeBag`: all of them, `size()`, `field()`, `getAny()`, `getLike()`, `classes()`, `styles()`, `fieldId()`, `modifier()` and `hasLike()`. atom no longer touches your attribute bag; its own components use an internal helper. A host component that called one of them reads the attribute itself (`$attributes->get('size')`, `$attributes->has('lg')`).

What stays: `Request::portal()`, `Str::namespace()`, `interval()` and `initials()`, `Arr::pick()`, and on the builders `whereDateBetween()`, `toPage()`, `toTable()`, `filter()`, `randomCode()`, `breakdown()`, `tableColumns()` and `tableColumnType()`. `tests/Feature/MacroAllowlistTest.php` pins the full list.

**Two dead declarations are gone.** The `editor` prop of `<atom:html>` and the shells (`layouts.sidebar`, `layouts.header`) was never read, because `<atom:tiptap>` links its own stylesheet: delete it from your markup (left in, it lands as an `editor` attribute on `<body>`). The provider also no longer registers a `database/migrations` path, which the package never had.

**atom:upgrade:** Automated: `date-use-line`, `html-editor-prop`. Reported: `date-pretty`, `date-local`, `date-recent`, `date-range-string`, `date-printed-bare`, `carbon-import`, `carbon-typed`, `macro-request`, `macro-str`, `macro-builder`, `macro-attribute-bag`. The codemod adds `Date::use(\Jiannius\Atom\Services\Carbon::class);` as the first statement of `AppServiceProvider::boot()`, with the `Date` import, when no service provider, file of `app/Providers` or `bootstrap/*.php` calls it. With no `AppServiceProvider.php`, no `boot()`, or another `Date::use()` already there, it changes nothing and says why. It deletes the `editor` attribute of `<atom:html>` and the shells. The date and macro sites are reported with `file:line` (once the line exists the date ones are review items); the macro calls need a decision of yours.

## JS globals

**atom no longer adds anything to the page's built-ins, and a call to one of the old helpers fails in the browser, not at build time.** The `Array`, `Number` and `String` prototype helpers, `window.dd` and `window.empty` are gone. Each helper is a function on `window.atom` that takes the value as its first argument, with the same behaviour and options:

| Before | After |
|---|---|
| `x.currency(symbol, round, maxPrecision)` | `atom.currency(x, symbol, round, maxPrecision)` |
| `empty(x)` | `atom.empty(x)` |
| `dd(...)` | `console.log(...)` |
| `rows.pluck('id')`, `.unique(attr)`, `.sum(attr)`, `.where(key, v)`, `.firstWhere(key, v)`, `.toggle(v)` | `atom.arr.pluck(rows, 'id')`, `atom.arr.unique(rows, attr)`, `atom.arr.sum(rows, attr)`, `atom.arr.where(rows, key, v)`, `atom.arr.firstWhere(rows, key, v)`, `atom.arr.toggle(list, v)` |
| `s.headline()`, `.limit(n)`, `.slug()`, `.camel()`, `.nl2br()`, `.striptags()` | `atom.str.headline(s)`, `atom.str.limit(s, n)`, `atom.str.slug(s)`, `atom.str.camel(s)`, `atom.str.nl2br(s)`, `atom.str.striptags(s)` |
| `s.toDateString()`, `.toDatetimeString()`, `.toTimeString()`, `.toDateFormat(format)` | `atom.str.toDateString(s)`, `atom.str.toDatetimeString(s)`, `atom.str.toTimeString(s)`, `atom.str.toDateFormat(s, format)` |
| `s.fromNow()` | removed, no replacement (see below) |

Search your JS and Blade (`x-text`, `x-bind`, `x-data`, `x-init`, `x-on`, `x-effect` and `<script>`) for `.currency(`, `.pluck(`, `.unique(`, `.sum(`, `.where(`, `.firstWhere(`, `.toggle(` on an array (a `classList.toggle()` is the browser's own), `.headline(`, `.limit(`, `.slug(`, `.camel(`, `.nl2br(`, `.striptags(`, `.toDateFormat(`, `.toDateString(`, `.toDatetimeString(`, `.toTimeString(`, `.fromNow(` (removed, see below), and for a bare `empty(` or `dd(` in JavaScript (a PHP `empty($x)` is unaffected). Notes:

- Every helper behaves as its method did for every value the method could be called on. `atom.arr.*` returns a non-array unchanged, and `atom.arr.toggle()` changes the array in place (so `atom.arr.toggle($wire.ids, 3)` still updates a Livewire array) and returns it.
- **`.fromNow()` is removed with no replacement.** It needs dayjs's `relativeTime` plugin, which atom has never loaded, so it always threw. If you want it, extend dayjs with `relativeTime` yourself and call `dayjs(value).fromNow()`.
- **Only difference: a `null` or `undefined` value no longer throws.** A method cannot be called on `null` or `undefined`, so the old calls threw a `TypeError`; the functions take the value as an argument and answer instead:
  - `atom.str.toDateString`, `toDatetimeString`, `toTimeString` and `toDateFormat` return `undefined` for `null` (as they do for any invalid date) and format the current moment for `undefined` (dayjs reads `undefined` as now);
  - `atom.str.nl2br(null)` and `nl2br(undefined)` return `''`;
  - `atom.str.camel`, `slug`, `headline`, `striptags` and `limit` still throw a `TypeError` on `null` and `undefined`;
  - `atom.currency(null)` is `'0.00'` and `atom.currency(undefined)` is `'NaN'` (the number is `Number(value)`, and `Number(null)` is `0`); `atom.currency('abc')` is `'NaN'` too.
- `atom.empty` is the function `window.empty` was: `null`, `undefined`, `''`, a blank string, `[]` and `{}` are empty; `0`, `false` and a `Date` are not.
- Nothing in atom's own markup or scripts uses the old names any more. `tests/Feature/JsGlobalsTest.php` fails if one comes back.

**atom:upgrade:** Automated: none. Reported: `js-currency`, `js-array-helper`, `js-string-helper`, `js-date-helper`, `js-from-now`, `js-empty`, `js-dd`. It lists every site that calls an old helper, in `.js` and `.ts` files and in the Alpine attributes and `<script>` blocks of Blade, and rewrites none of them: an expression inside an Alpine attribute is not safe to rewrite by regex. A match is a candidate (`.toDateString(` is also a native `Date` method).

## The legacy editor: `AsEditorContent` and `<atom:editor*>`

**`Jiannius\Atom\Casts\AsEditorContent` is deleted, and so are `<atom:editor>`, `<atom:editor.chat>` and `<atom:editor.content>`** (they were aliases of the `tiptap` components), and the built `editor.css` that nothing linked. `AsTiptapContent` keeps its name and keeps reading what the old cast stored (`serialize()`d HTML, and `serialize()`d JSON for a field that was `<atom:editor>`), so a column moves in two steps and never in one big bang.

**Do this on 3.x first, before you require v4** (the minor that ships `atom:tiptap-migrate` v2; do not move a column to v4 still cast as `AsEditorContent`: the class is gone, Laravel ignores a cast it cannot resolve, and the attribute silently reads as the raw `serialize()`d string):

1. Switch the casts from `AsEditorContent` to `AsTiptapContent`. Nothing is converted yet; the same rows read the same. **Change each editor column to `longText`**: the JSON is about 3.5 times the HTML, so an old value over about 18 KB cannot fit a MySQL `TEXT` (65,535 bytes); the command refuses such a row and says so. Run the command with the app's own database connection settings, since a connection charset that differs from the column's can mangle what is read.
2. `php artisan atom:tiptap-migrate`: a dry run. **A plain run is a dry run now**: in 3.x a plain run wrote, so a deploy script that ran it stops migrating until it passes `--force`. It lists every value as clean, flagged (it would lose something: a class, an inline style, a `<font>`, a `<script>`, an unknown tag) or refused (a serialized object, JSON that is not a document, a value over the limits), and writes nothing. Read the flagged rows; fix the refused ones by hand.
3. `php artisan atom:tiptap-migrate --force` converts the clean rows. Each original is backed up first, in `atom_editor_backups` (created on the model's own connection), in the same transaction as the update, and `updated_at` is not touched. Convert flagged rows you have read with `--accept=<ids>` (or `--accept=all`). `--restore[=ids] --force` puts rows back byte for byte.
4. `php artisan atom:tiptap-migrate --compare` writes a JSON Lines review file (`storage/app/atom-editor-review-<time>.jsonl`): per migrated row the original HTML, the new HTML, and the difference in text and in tags and attributes. Review it yourself, or ask Claude in your project to read it and list what is missing from each `new_html`.
5. `php artisan atom:tiptap-migrate --prune-backups` deletes the backups, only once you have signed off. It always asks in a terminal; without one it needs `--confirm-prune` (`--force` does not confirm it), and it leaves the empty `atom_editor_backups` table for you to drop. Until then `atom:purge-editor-images` keeps every image a backup still names.
6. `php artisan atom:tiptap-migrate --status` exits 0 when nothing is left.

**Flags and exit codes.** `--force`, `--accept=<ids|all>`, `--restore[=ids]`, `--discard-edits`, `--compare[=ids]`, `--output=`, `--prune-backups`, `--confirm-prune`, `--status`, `--model=`, `--column=`, `--path=`. A row id that is in more than one model or column is refused until `--model` and `--column` narrow it. `--force` exits 1 when a write failed or a refused value remains; `--restore --force` exits 1 when it skipped a value (an edited row, a row that is gone, a missing model class; `--discard-edits` overrides the edited case); `--status` exits 1 until nothing is left; `--dry` is refused with `--restore` and `--prune-backups`.

Then on v4: `<atom:editor*>` becomes `<atom:tiptap*>`, with the same props. A column that still has serialized values keeps rendering (`AsTiptapContent` reads them) but is not migrated; the purge command stops, and names the column, if one is still cast as `AsEditorContent`.

**Static prose wrapped in `<atom:editor.content>` is re-parsed by the editor schema and loses its markup.** Use a plain element with the `text-base` reading role instead (`<div class="text-base">`).

**atom:upgrade:** Automated: `editor-tag`. Reported: `editor-cast`, `editor-content-static`. The codemod renames `<atom:editor>`, `<atom:editor.chat>` and `<atom:editor.content>` (opening, closing and self-closing, and the `<x-atom::editor*>` spelling) to `tiptap`, leaving Blade comments and other tags such as `<atom:editor-toolbar>` alone. It does not touch a cast, and it does not migrate data: it refuses to write at all while `php artisan atom:tiptap-migrate --status` is not ready (see "The order", step 4).
